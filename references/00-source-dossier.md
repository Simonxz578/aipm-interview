# A. 视频一：AI 产品面试被问 Skill，怎么体现自己的认知

核心问题：面试官问“怎么理解 Skill”，候选人应该理解到什么程度？

## 完整语义整理

很多 AI 产品面试会问对 Skill 的理解。这个问题不只是考一个名词，它会把技术理解和产品理解结合起来。如果只会背技术原理，产品问题依然答不好；如果完全不懂技术，也解释不清为什么机制有价值。

一个常见初级回答是：
“Skill 不就是一个丰富版的 Prompt 吗？”

但只停在这里不够。

从 Prompt Engineering 的瓶颈看，如果不断把规则、知识、工作方式全部写进一个越来越长的 Prompt，会出现：
1. 与当前任务无关的知识也被塞进上下文，模型注意力被稀释；
2. 大量业务知识、具体项目知识同时加载，上下文成本高；
3. 切换场景又要重新写 Prompt，很麻烦；
4. Prompt 很难变成可复用、可发现、可维护的专业能力。

Skill 要解决的是：
**把 Agent 的专业能力，从一次性 Prompt 变成模块化、可发现、可复用、按需加载的能力。**

### 特性一：可触发 / 可发现
通过 name + description 等元信息，让 Agent 判断当前任务是否应该调用这个 Skill。
不是所有能力每次都加载。

### 特性二：渐进式加载
不是把所有知识同时进入模型上下文。
更合理过程：
发现 → 激活 → 执行 → 按需加载具体资源。
否则 Skill 和知识越来越多后，上下文扛不住。

### 特性三：Skill 不只是知识
一个 Skill 可以明确：
- 按什么步骤执行；
- 哪些动作必须做；
- 哪些动作禁止做；
- 可以调用哪些工具；
- 哪些固定动作交给脚本；
- 用哪些参考资料或业务规则。

所以 Skill 更像“专业工作方法 + 资源 + 执行约束”的封装。

### 什么值得 Skill 化
判断方向：
1. 是否反复发生；
2. 是否有稳定、专门的做事方法；
3. 步骤能否明确；
4. 是否会固定调用工具或数据；
5. 是否有公司模板、数据口径、固定规则要复用；
6. 是否因为缺少约束和工作流程导致输出不稳定。

一次性任务或一句 Prompt 已经稳定完成，不必 Skill 化。
每次都必须遵守的全局规则，更可能适合 System Prompt。
特定任务触发的专业流程，更适合 Skill。

### 面试应该体现的认知
不要只说“Skill 是 Prompt 升级版”。
要能说清：
- Prompt 的上下文和复用瓶颈；
- Skill 的触发；
- 渐进式加载；
- 任务边界；
- 标准工作流；
- 资源/工具/脚本；
- 什么适合 Skill，什么不适合；
- Skill 如何提升专业任务的稳定性。

# B. 视频二：AI 产品的 PRD 怎么写

核心：AI PRD 和传统 PRD 的区别，不是“传统 PRD 多加一章 AI”。

## 完整语义整理

AI PRD 首先仍然要回答业务价值在哪。

但 AI 产品多一个关键问题：

> **为什么一定要用大模型？**

需要说清：
- 大模型在这个场景里的不可替代性是什么；
- 是效果更好、成本更低、输入更复杂、规则无法穷举，还是开放语义/多模态必须依赖模型；
- 传统方案为什么不够。

以电商素材生成为例：
先梳理核心业务问题；
拿数据说明问题；
再说明 AI 素材为什么可行，而不是先上模型再找理由。

之后仍需要竞品分析和产品目标。

### 业务目标 vs 模型目标

智能客服业务目标可能是：
- 问题解决率提升；
- 人工成本下降；
- 服务效率提升。

模型目标可能是：
- 回复准确率；
- 对话轮次；
- 拒答/升级人工；
- 任务完成质量。

模型目标必须服务业务目标。

### 需求和流程
PRD仍要写核心功能、优先级、性能、响应速度、安全和数据需求。

业务流程是用户视角的操作步骤和业务执行落地步骤。

系统流程尤其重要。
Agent要标出：
- 大模型调用节点；
- 工具调用节点；
- 判断/路由节点；
- 人工介入节点；
- 异常处理分支。

### 模型选型
重要原则：
**从小参数模型开始验证；效果相似时优先小模型。**

Agent多个节点可用不同模型：
- 复杂推理强模型；
- 分类/抽取小模型；
- 主模型 + 备用模型；
- latency / cost / QPS / context / structured output / multimodal 共同决定。

### Prompt 工程
Prompt必须文档化管理，不能当“调试时再说”。

PRD应明确：
- System Prompt角色；
- 能力边界；
- 输出约束；
- 核心指令；
- 示例；
- Prompt策略；
- 版本管理。

硬规则：
**未经评测的 Prompt 不能直接上线。**

### 评测体系
评测是 AI 产品的核心专业资产之一。

需要：
- 数据来源；
- 核心/边界/对抗/安全场景比例；
- MVP/灰度/全量所需评测规模；
- 每个维度评分方式；
- 人评、自动规则、LLM-as-Judge组合；
- Prompt/模型升级/Bad Case触发回归。

不能只写“准确率”。

### 效果保障与稳定性
模型输出到用户看到结果之间要有质量控制：
- Structured Output / Schema；
- 格式校验；
- 后处理；
- 多次采样/一致性；
- RAG引用；
- cross-check；
- 置信度/拒答；
- fallback；
- timeout；
- 限流；
- cache；
- failover。

### AI能力边界
PRD要明确：
- 能做到什么；
- 做不到什么；
- 已知缺陷；
- 当前版本不修什么；
- 哪些必须人工确认。

### 数据飞轮
用户使用 → 数据采集 → Bad Case → 评测集更新 → 问题归因 → Prompt/模型/流程优化 → 效果提升。

### 上线与运营
还要考虑：
- 灰度/AB；
- 成本；
- 回滚；
- 风险。

AI PRD可以很细，但实际工作按项目风险和阶段裁剪，不要求每次写满所有章节。

# C. 14页《大模型产品模板 PRD》章节

1. 背景：业务背景、为什么用大模型、竞品、产品目标  
2. 需求描述：需求清单、功能/性能/安全/数据  
3. 业务流程图  
4. 系统流程图  
5. 模型选型  
6. Prompt 工程  
7. 训练数据集（如涉及）  
8. 评测体系  
9. 效果保障与稳定性  
10. 原型图  
11. AI能力边界  
12. 数据飞轮  
13. 上线与运营  
14. 风险  
15. 附录：术语、评测集、Prompt文档
