# 面试答案的组织与深度

本文件用于选重点、核对证据和组织答案。面试口述不展示框架名称；只有用户要求提纲或解析时，才展开框架。保留判断优先级：业务判断 > 产品机制 > AI架构 > 评测与ROI > 概念定义。

## 1. Product 8 Questions

| 内部问题 | 要作出的判断 |
| --- | --- |
| WHY / Problem | 当前怎么解决、baseline是什么、不解决的代价；先确定值不值得做。 |
| WHO / People | 使用、付费、决策、承担错误后果的人分别是谁；目标是否冲突。 |
| SCENE / Job | 哪个高频具体场景、要完成什么任务；口头需求有没有行为证据。 |
| AI FIT | 对比规则、搜索、固定Workflow、人工和传统ML；此处能否承受模型不确定性。 |
| PRODUCT + SYSTEM | 用户走哪几步；模型、规则、知识、工具和执行控制分别做什么。 |
| PROOF | 离线任务表现、线上行为、业务或学习结果怎样连接；什么条件才可上线。 |
| ECONOMICS + RISK | 延迟、算力、审核、维护、错误代价；确认、降级、回滚如何设计。 |
| ITERATION | 错误如何归因、进入Eval、回归、灰度；何时扩大或收紧自主权。 |

先说优先解决什么及原因。复杂题先用一两句交代全局，再选择最影响结果的一条分支深入；通常展开3–5个相关环节，不平均讲八点。时间不足时缩范围，保留动作与验证。

## 2. WSTAR-RT：行为题和项目题

| 环节 | 内容与边界 |
| --- | --- |
| What | 一句话交代哪件事、解决什么、真实结果到哪一步。 |
| Situation | 只留理解行动所需的用户、业务、时间和约束。 |
| Task | 我的目标、困难、责任边界、成功标准。 |
| Action | 占主回答50%–65%；2–4步写清我做了什么、为什么、取舍与调整。 |
| Result | 量化结果要有口径；无商业数据可讲交付、公开Beta、论文发表等真实产物。 |
| Reflection | 哪个判断改变了，重做会怎样；不得编造后来已实施的改进。 |
| Transfer | 岗位相关时补一句能力迁移，不必每题强行加。 |

回答前选一个有足够行动证据的故事。Action不足50%时重写，删去过长背景，补充已有行动的原因和边界；材料不足就换故事、询问关键事实或明确改用假设方案，不能靠虚构行动凑长度。第一作者身份不能推出独立完成招募、访谈、编码或所有修订。

## 3. 行为能力覆盖

这里的“宝洁八大能力”是求职训练标签，不是P&G当前官方固定八题。官方招聘页面确认使用行为面试；官方设计岗位面试指南要求交代背景、行动、结果，并说明个人贡献和行动理由。[招聘流程](https://www.pgcareers.com/global/en/hiring-process)、[设计岗位面试指南](https://www.pgcareers.com/us/en/design-interview)。核验日期：2026-09-21。

| 标签 | 寻找的证据 |
| --- | --- |
| demanding_goal | 困难目标、持续推进、真实完成结果 |
| leadership | 主动承担、协调资源、推动共同目标 |
| analysis_planning | 搜集信息、识别关键变量、制定可执行步骤 |
| influence | 用事实处理分歧；必须有真实对象、分歧与行动 |
| collaboration | 与他人协作的具体接口和自己的贡献 |
| innovation | 新方法改变了什么，如何验证 |
| prioritization | 资源约束下舍弃什么、保住什么 |
| learning_agility | 新技能怎样用于实际任务并得到反馈 |

标签只用于检索故事和诊断薄弱项。没有领导、冲突或审稿协作证据时，不为覆盖标签编故事。

## 4. Answer depth router

| 模式 | 主口述长度 | 大致时间 | 必须讲到 |
| --- | --- | --- | --- |
| quick：定义、单点追问 | 180–280中文字符 | 40–60秒 | 直接结论、2–3要点、产品含义或取舍 |
| standard：普通业务题 | 320–520中文字符 | 75–120秒 | 判断、原因、具体方案、验证、取舍；一般不少于250字 |
| scenario：设计、指标异常、技术选型 | 450–700中文字符 | 2–3分钟 | baseline、核心动作、指标、fallback |
| deep-dive：项目、行为题 | 600–900中文字符 | 2.5–4分钟 | WSTAR-RT；Action占50%–65%，结果有证据，带反思 |
| pressure follow-up：压力追问 | 先一句直答，再120–250中文字符 | 随问题收窄 | 只解释被追问的假设、证据或取舍，不重讲整题 |

字数是口述主回答的密度目标，不计标题、考点、追问和来源。时间只是估算，随语速变化。用户指定30秒、90秒、长版、简答或提纲时优先遵守；真实性优先于补字数。

用自然普通话，每段有因果和具体动作。可用2–4个自然分点，但连起来应能直接说给面试官听。避免“不仅……而且……”“不是……而是……”式套话、赋能、抓手、全链路、闭环生态和自夸。每题至少有明确判断、具体动作或机制、验证方式/指标/结果。复杂题再检查风险或取舍。

## 5. AI功能开工前四问

输入是什么：文字、图片、音频、视频及其质量、授权和预处理，决定模型及数据链路。

延迟预算多少：用户等的是首个反馈还是完整结果；结合任务测试等待容忍度，决定同步、异步、流式、缓存与模型分工。不能把某个产品的“三秒”当所有场景红线。

失败怎么办：哪些可重试，哪些降级到规则/模板，哪些不展示或转人工；有副作用的操作先查执行状态，避免重复提交。

怎么算成功：定义目标用户完成什么、验收样本与质量门槛；生成率不等于采纳率，采纳率也不直接证明转化或学习效果。

## 6. 风险管理：上线前、线上、事后

上线前列能力范围与明确禁区，按后果分级，验证回滚/降级开关，限定场景和小流量灰度。人工确认按风险与可恢复性配置，不要求所有功能逐次人工审批。

线上同时看质量、成本、用户体验与投诉；分人群和任务，避免平均数掩盖严重错误。明确监控责任人、告警、暂停与恢复条件。

事后先止损、恢复服务，再定位与复盘。保存版本和必要trace，控制访问范围。复盘要落到缺失的测试、规则、权限或流程以及负责人、验证与完成时间；仅说“加强测试”不够。

## 7. Failure consequence taxonomy

| 失败 | 先检查 | 控制措施示例 |
| --- | --- | --- |
| 调错工具 | 任务路由、工具描述、越权 | 限定可用工具，阻断未授权动作 |
| 参数错误 | 类型、单位、对象ID、业务约束 | Schema与规则检查，高风险提交前确认 |
| timeout / infra | 服务状态、超时后是否已经执行 | 有上限重试、退避、查询状态、服务降级 |
| 重复执行 | 业务请求ID、状态与幂等性 | 幂等键、去重、事务与补偿 |
| 高风险业务动作 | 损失、可撤回性、受影响对象 | 更严格门槛、人工责任、审计与停止开关 |

先定义失败类型与后果，再约定每类分子、分母、时间窗、严重程度和触发动作。分别报告单次调用失败与任务最终失败，不能靠重试稀释失败率。天气查询与扣款不共用阈值；数值必须来自业务损失、基线和样本，不抄“千分之几”。

## 8. Bad Case四层归因

1. Data / Knowledge：资料缺失、过时、错误或权限不对；修来源、版本与授权。
2. Retrieval：资料存在但没召回、噪声过多、排序错误；检查解析、切块、索引、召回和rerank。
3. Model / Prompt：正确证据已给但理解、推理、指令遵循或结构输出失败；修改对应节点并回归。
4. Product / Interaction：用户没有确认、纠错、退出路径，或能力边界不清；修流程和交互。

必要时追加Tool、Infra、Safety子类。一例可有多个原因，要记录主因、次因与可复现证据；按团队实际职责分配负责人，不把某一层永久归给某一岗位。每次只改变可归因的关键因素，并同时检查原有成功样本。

## 9. Agent评测：结果、过程、代价

结果：定义可验收的任务目标、正确性与权限边界，报告任务成功率和严重错误。满意度只能辅助解释。

过程：轮次、绕路、死循环、超时、重试、工具错误、人工介入；C端再看实际与感知等待、取消和流失。

代价：成功任务单位成本 = 同一统计范围内全部任务的推理、API、算力、重试、审核等总成本 / 成功完成的任务数。分母为零时不可计算，不报告零成本。固定研发投入另行摊销，延迟影响避免重复计价。

上线已有数据时优先采集真实Bad Case，并补正常、长尾、边界和高风险样本；冷启动用合法取得的真实任务及人工构造的边界样本。开发集与留出集分开，同一输入可重复测试稳定性。每次迭代回归，样本量按覆盖和统计不确定性确定，不声称固定500条足够所有业务。

## 10. PMF先检查能力基线

先验证任务完成、重复成功、重试和用户修正负担、关键错误及严重后果；比较原来人工、规则或现有工具的完成质量与成本。能力合格后看目标人群的留存、真实付费、渠道效率、使用频次。新鲜感、一次好评和免费试用不等于PMF。

壁垒可从合法积累的数据改进机制、工作流入口、私域知识、领域Eval、分发、习惯、组织集成和治理讨论。必须说明如何形成、是否可复制、维护成本；模型分数高不能单独证明壁垒。

## 11. Prompt / RAG / SFT按层选择

Prompt改当前行为、格式和判断，试验快但有推理与回归成本。RAG改可访问知识，适合动态、私有、可引用内容，风险在解析、权限、召回、排序及冲突。SFT改高频稳定行为，要求合法高质量数据、稳定场景和可验证收益，训练、更新与回归投入更大。

先用Bad Case定位，再决定改哪层；三者可组合。实时天气需要真实数据接口或可靠检索，不能只用Prompt补实时事实。模型自报confidence未经校准，不可直接作为业务概率或自动执行依据。AI产品仍需版本记录、实验对照与回滚边界；规模增长也不会自动消除推理和审核成本。

## 12. 困难题：What → Why → How → How Better

开头直答困难；说明约束为何冲突；把已有解决行动拆成三步，每步有理由与结果；最后说明下次会提前改变什么。技术困难不要只列安装库、模型名称或代码行数。没有真实事故记录时，讲已确认的困难与应对，不补造一场事故。

## 13. 缺点与动机

缺点：真实不足 → 造成过的具体影响 → 已采用的纠正机制 → 目前改善和仍待补足的部分。不能把完美主义或“过于负责”包装成缺点；没有量化跟踪就直说，不虚构改善百分比。

公司动机：JD核心问题 → 我的相关证据 → 这家公司的具体业务为什么适合发挥 → 我希望补足什么。岗位与公司事实必须查最新官方来源。缺JD时先给可用的通用岗位回答，说明可按JD调整，不编公司战略或业务数据。
